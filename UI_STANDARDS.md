# Nexus PORTAL control-help standard

Every button, input, dropdown, textarea and other editable control must explain its function and practical effect for a beginner. This is a standing product requirement for existing and future options.

- Static controls carry explicit `data-help` descriptions in `dashboard/portal_preview.html`. Explain what changes, when it takes effect, and relevant limits or costs. Use plain language; distinguish reading data, saving configuration, modeling a trade and making a paid AI request. Do not promise profitability or market execution.
- Create dynamic buttons through `helpButton(description)`. Provide descriptions for any other dynamic input/select/textarea. New controls without meaningful help fail coverage or factory checks; the runtime fallback is a diagnostic fallback, not finished product copy.
- The noninteractive description panel stays at the bottom right, with a solid black background, bright purple text, readable 16 px typography and strong contrast. It must fit small windows and wrap long words. Do not add glow or animation that weakens legibility.
- Show help on pointer hover, including disabled controls. Hide it when the pointer leaves the control, keyboard focus leaves, Escape is pressed, the window loses focus or the control is removed. Preserve help during automatic scrolling while the control remains visibly hovered or keyboard-focused; hide it if the control is no longer hovered/focused in view. Nested content inside a button must not cause flicker. Keyboard focus also shows help and connects it with `aria-describedby`, preserving any existing descriptions.
- Hover/focus must never activate controls, send requests, change settings, show input values or expose credentials. Describe a password field’s purpose without reading or echoing its value.
- Keep this reference in source so another development session can continue the same standard.

Validation: run `python -m pytest -q tests/test_control_help.py`, `node tools/control_help_smoke.cjs`, the full regression suite and PORTAL script `node --check`. The tests cover all static controls, the dynamic-button factory, color contrast and actual help-controller event behavior. Browser checks additionally verify placement, hover-off, focus, disabled and dynamic controls at desktop and narrow viewport sizes. Native Windows visual acceptance remains a separate release gate.

Real-browser acceptance is implemented by `tools/portal_browser_smoke.py`. Install optional tooling with `python -m pip install -e ".[dev,ui]"`, then `python -m playwright install chromium --only-shell` and run `python tools/portal_browser_smoke.py --output browser-evidence`. An optional `--channel msedge` can use an installed Edge browser. The tool intercepts the entire page and all API responses with local fixtures; it never starts the backend or uses account/feed data. It checks visible static/dynamic/disabled controls, dropdown selection, focus/Escape, private-value isolation, black/purple styles, clipping and bottom-right placement at 1280×900, 390×844 and 320×568. Reports include the actual HTML SHA-256, CI commit and Playwright version.

Windows safety CI runs this check and retains screenshots/report for 30 days, including a failure screenshot if a page assertion fails. A missing browser or download failure fails the check rather than silently reporting a pass. Headless browser evidence does not replace native Windows-window, clean-profile or human legibility acceptance.

Workspace navigation: use labeled ARIA tabs with matching panels and one selected tab; support Left/Right/Home/End and visible keyboard focus. Keep stop controls outside hidden panels. Tabs preserve existing form/session state and do not trigger setup actions. Automatic checklist boxes are disabled, have practical data-help and readable row descriptions; they reflect scoped server observations, never user assertions or trade permission. Clear previous ticks while refreshing or after failed verification.

The Accounts broker request recovery diagnostic uses a separate temporary fixture and actual controller check (`node tools/broker_request_smoke.cjs`). It must remain explicit, prevent repeated clicks while pending, restore the button after errors, show retained partial quantity and disconnected scope, and never display raw storage/provider errors. Browser acceptance intercepts the fixture response and exercises the button without backend/account IO.

The broker fee fixture now also reports a retrospective fee-reserved funding path. Keep the explicit supplied-history label, separate unverified spendable funds/account status, review fallback for missing path data, duplicate-click guard and sanitized errors. Reuse the broker controller check and intercepted Accounts traversal; do not imply a covered fixture verifies deposits or authorizes spending.
